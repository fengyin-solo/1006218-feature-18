# 水电站机组运行检修管理平台

面向电站台账、机组运行、调速励磁、主变与闸门、大坝渗流位移监测、机组检修与发电计划的一体化水电站运行检修管理平台。

这是一个**纯前端**管理平台：Vue 3 + Vite + TypeScript，仓库里没有后端服务。业务数据由
`frontend/src/data/` 下的本地数据层提供：首次打开用示例数据播种，之后的登记、筛选与状态流转
结果都持久化在浏览器 `localStorage` 里，刷新或重开浏览器都还在。dev server 已关掉自动打开页面，
启动后按终端打印的地址手工打开。

## 目录结构

```text
.
├── frontend/                 Vue 3 + Vite + TypeScript 前端（唯一运行单元）
│   ├── src/views/            每个业务模块一个页面
│   ├── src/api/local-service.ts   本地数据服务：列表、筛选、动作流转、导出
│   ├── src/data/             模块元数据 / 示例数据 / localStorage 持久化
│   ├── src/stores/           会话与筛选状态
│   └── vite.config.ts        dev server 配置（open: false，无 /api 代理）
├── .gitignore
└── docker-compose.yml
```

## 启动

```bash
cd frontend
npm install
npm run dev
```

前端默认监听 `http://127.0.0.1:5173/`，dev server 不会自动打开浏览器，需要自己访问。

生产构建：

```bash
cd frontend
npm run build
```

## 约定

- 每个模块的页面在 `frontend/src/views/<模块>/index.vue`，页面只负责渲染，读写统一走
  `frontend/src/api/local-service.ts`。
- 字段、状态、动作与流转目标集中在 `frontend/src/data/modules.ts`；示例数据在
  `frontend/src/data/seed.ts`。
- 状态流转只允许在 `local-service.ts` 里改，页面组件不做业务判断。
- 想回到初始数据：清掉浏览器里 `hydropower-plant-om:entries` 这一项，或调用 `resetModule(模块)`。

## 汛期水情空值处理（`frontend/src/domain/`）

水情调度、泄洪操作、缺陷处置三个模块在通用脚手架之上加了一层领域逻辑，独立持久化在
浏览器 `hydropower-plant-om:domain-v1`，业务规则全部在服务层，页面不做判断。

### 空值口径

- 上游水位、下游水位、入库流量、出库流量四个量测项统一用 `HydValue` 表示：取不到就是
  `value: null` + 失败原因（超时 / 测站离线 / 链路中断 / 数值失真弃用），**绝不写 0**。
- 真实的零必须由值班员显式勾选「确认真实零」才落库，页面显示 `0（真实零）`；随手填的
  未确认 0 一律按空值处理。页面上缺测项显示黄底「暂无数据」并附失败原因，空值记录与
  实数记录分两张表列出，不混排。
- 取数失败可以「重试」；某量测项通道**连续中断超过 1 小时仍为空 → 禁止提交观测**，必须先
  人工补测（补测写入实数并清空中断计时），补测完再走调度。
- 流量平衡校验只让实数参与：入库或出库任一缺测就不出平衡差，明确写出「空值不参与平衡校验」。
- 调度建议兜底：**上游水位、入库流量**缺测时，自动取观测时间更早的最近一时段实数兜底，
  建议文本注明「兜底值」及来源记录号；找不到前值则不兜底、必须补测。兜底只影响调度建议，
  不改观测原值。
- 今日入/出库合计等统计只累加实数，全天全空时显示「暂无数据」而不是 0。

### 环节顺序（跳级一律拦下，提示缺的环节）

- 水情：待观测 → 已观测 → 已调度 → 已复核（提交观测、下达调度、提交复核）。
- 泄洪：待审批 → 已批准 → 泄洪中 → 已结束。
- 缺陷：待处理 → 处理中 → 已消除 / 已挂账。

### 回写与对账（两处条数同源）

- 水情「提交复核」的结论会回写到指定泄洪操作单的**调度待办**；泄洪页待调度数与水情页
  调用同一个 `pendingDispatchCount()`（未复核记录 + 复核后未处理待办），两个页面永远对得上。
- 缺陷「确认消除」的处理结论回写**现场巡视隐患清单**；隐患清单页面条数与 CSV 导出行数
  来自同一个过滤结果。所有导出文件名直接带条数。

### 重复上报与重试

- 水情：同一观测时间（精确到分钟）重复上报**只保留最后一次**，按观测时间覆盖，记录号
  不变并保留覆盖历史；同时段永远只有一条。
- 缺陷：缺陷编号相同、或「设备名称 + 业务日期 + 缺陷描述」完全相同即判重，**只认第一次
  取值**，后到的按重复处理并写入「重复上报留痕」，不覆盖既有记录。
- 重试幂等：登记/提交带 `clientToken`，同一令牌重试直接回放已落库结果，绝不重复登记。

### 存量迁移方案（顺序与缺项规则）

迁移代码：`frontend/src/domain/migration.ts`，存量样本：`legacy-dump.ts`，按 localStorage
版本号幂等执行（`MIGRATION_VERSION`）。

迁移顺序（由回写依赖决定）：

1. **水情记录 hydrology** —— 先落观测主体并产出缺数清单；
2. **泄洪操作 flood** —— 复核结论要回写它的调度待办，必须在水情之后；
3. **缺陷处置 defect** —— 处理结论回写现场巡视隐患清单，隐患清单随缺陷一起建立。

每个模块内部都**按业务日期升序回填**（水情/泄洪按观测、操作时间，缺陷按发现日期）。

缺项识别规则：

- 水情量测项的裸 `0`（`"0"`/`0`，无单位、无确认标记）一律判为「早期把缺数随手写成 0」→
  置空，原因记 `legacy_zero`，原始值保留在 `legacyRaw` 可审计；无法解析为数值的脏值
  （如「通讯中断」、`--`）置空，记 `legacy_unparsable`。真实的零无法与裸 0 区分，统一进入
  缺失字段清单，由人工补测确认后以「真实零」重新登记。
- 缺陷/泄洪的空串、`--`、`null`、`undefined` 判为字段缺失，不伪造默认值，单独列入缺失清单。
- 缺失清单可在「水情调度 / 缺陷处置」页面查看并导出，与迁移报告 `migration.issues` 同源。

新系统播种时还会附带一批割接后的当值演示数据（含「中断 95 分钟待补测」场景），编号
1xxx；存量迁移记录编号为 8xxx，不计入迁移报告统计。
